# Runtime performance qualification — 2026-09-20

This is a local qualification record for the Phase 1–3 performance campaign,
not a portable CI threshold or a replacement for the historical baseline.
The timings below are same-host observations from equivalent local fixtures;
they are not promises about every machine or workload.

The TLS connection comparison is the plan's permitted component fallback, not a
full supervisor benchmark. It uses a running local TCP listener with startup
outside the timed region. The baseline shape parses PEM and builds a server
configuration for every accepted connection; the optimized shape clones a
prepared `Arc<ServerConfig>`. The prepared-listener handshake alone measured
490.54 µs (458.18–515.35) on the baseline and 412.66 µs (403.35–418.56) on
the optimized tree; this is retained as supporting component evidence rather
than attributed to the production supervisor in isolation.

## Relay buffer matrix

The optimized single-owner relay was run with explicit `relay_with_options`
buffer sizes. These are steady local fixture medians; all four workloads use
the same listener/echo topology.

| Buffer | 1 KiB | 64 KiB | 1 MiB | 16 × 64 KiB |
|---:|---:|---:|---:|---:|
| 16 KiB | 127.80 µs | 455.91 µs | 1.213 ms | 606.19 µs |
| 32 KiB | 115.60 µs | 185.60 µs | 979.37 µs | 512.90 µs |
| 64 KiB | 118.55 µs | 173.44 µs | 816.48 µs | 520.36 µs |

Lower buffers are not uniformly better: 16 KiB is materially slower for the
64 KiB and 1 MiB transfers, and 32 KiB remains about 20% slower than 64 KiB
for 1 MiB. The decision is therefore `retain-64k-supported`; the production
compatibility setting remains unchanged. This result does not authorize a
future tuning change without a separate plan.

### Deterministic relay-buffer allocation

This is allocation arithmetic, not an RSS measurement. Each active relay owns
two directional buffers, so the buffer allocation is `2 * buffer_size`:

| Buffer | Per active relay | 100 active relays | 1,000 active relays |
|---:|---:|---:|---:|
| 16 KiB | 32 KiB | 3.125 MiB | 31.25 MiB |
| 32 KiB | 64 KiB | 6.25 MiB | 62.5 MiB |
| 64 KiB | 128 KiB | 12.5 MiB | 125 MiB |

## Commands and interpretation

The standard comparison commands were:

```bash
cargo bench --bench tls_setup -- tls_setup --sample-size 10 --warm-up-time 0.1 --measurement-time 0.1
cargo bench --bench route_match -- route_select --sample-size 10 --warm-up-time 0.1 --measurement-time 0.1
cargo bench --bench udp_relay -- udp_runtime --sample-size 10 --warm-up-time 0.1 --measurement-time 0.1
cargo bench --bench tcp_relay -- steady --sample-size 10 --warm-up-time 0.1 --measurement-time 0.1
```

The route one-member follow-up used the same filters with
`--sample-size 20 --warm-up-time 0.3 --measurement-time 0.3`. The buffer
matrix used `tcp_relay_buffer_matrix` with the standard settings.

These results distinguish measured wall-clock observations from deterministic
memory calculations and qualitative structural evidence. They are local
qualification observations, not mandatory CI thresholds. CI remains a
correctness/quality gate; it does not enforce these numbers.

## Intentionally unchanged costs and scope

- The compatibility relay facade still owns two 64 KiB buffers and its
  bounded one-second drain.
- UDP datagram ownership/allocation remains unchanged; no pooling was added.
- HTTP forward upstream connection reuse remains deferred.
- No public Rust API, configuration schema, protocol behavior, routing policy,
  TLS verification policy, UDP limit, pproxy behavior, or reload semantics
  changed in this evidence pass.
